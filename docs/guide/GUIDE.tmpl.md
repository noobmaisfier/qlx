## 1. Principe

1. Vous écrivez votre schéma en SQL (migrations) ; `qlx gen` le lit et génère du Go typé : tables, colonnes, lignes, insertions, patchs, enums, fonctions.
2. Vous écrivez vos requêtes avec des builders Go qui ressemblent à SQL ; le compilateur vérifie les types et la nullabilité, le rendu vérifie la portée des colonnes, le groupement et les versions de PostgreSQL.
3. Aucune API n'accepte du texte SQL : ce qui n'est pas modélisé ne peut pas s'écrire. Les valeurs sont toujours des paramètres `$n`, jamais concaténées.

Un exemple complet tient en quelques lignes :

```go
rows, err := client.All[UserRow](ctx,
    q.Select(Users.ID, Users.Email).
        From(Users).
        Where(Users.Tier.Eq("pro")).
        OrderBy(Users.CreatedAt.Desc()).
        Limit(20))
```

Pas de `Prepare`, pas de cache à déclarer : la forme de la requête est reconnue au deuxième appel (voir §8).

## 2. Démarrage

### 2.1 Les commandes

```
qlx init     # écrit qlx.yaml et migrations/001_init.sql (n'écrase jamais)
# ... écrivez votre schéma dans migrations/*.sql ...
qlx gen      # applique les migrations sur un serveur jetable, écrit schema.lock + le paquet Go
qlx check    # échoue si le code généré ou schema.lock est périmé ou modifié à la main
```

| Commande | Rôle |
| --- | --- |
| `qlx init` | crée `qlx.yaml` et une première migration, sans jamais écraser |
| `qlx gen` | génère le paquet Go et `schema.lock` ; `-from-lock` régénère sans aucune base |
| `qlx check` | CI : le code généré correspond-il aux migrations ? (sans base) |
| `qlx verify` | CI : une base vivante correspond-elle à `schema.lock` ? |
| `qlx watch` | régénère à chaque modification de `migrations/` ou de `qlx.yaml` |
| `qlx doctor` | liste les outils manquants, avertissements et objets non gérés |
| `qlx prepare` | fait `PREPARE` de chaque requête d'un fichier `qtest.Dump` sur un vrai serveur |
| `qlx rows` | génère `ScanTargets` pour vos structs marquées `//qlx:row` |
| `qlx sql2go` | convertit du SQL en code QLX (compilé avec `-tags sql2go`) |
| `qlx regress` | traduit les requêtes de la suite de régression PostgreSQL (`-tags sql2go`) |

`qlx -config autre.yaml <commande>` choisit un autre fichier ; `.yml` et `.json` sont aussi lus.

### 2.2 Un schéma d'exemple

```sql
-- migrations/001_init.sql
CREATE TABLE users (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email      text NOT NULL UNIQUE,
    nickname   text,                              -- nullable
    tier       text NOT NULL DEFAULT 'free',
    balance    bigint NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE orders (
    id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users (id),
    total   bigint NOT NULL,
    status  text NOT NULL
);
```

### 2.3 `qlx.yaml`, clé par clé

```yaml
package: db                 # paquet Go généré
out: db                     # répertoire de sortie
schemas: [public]           # schémas lus
migrations: migrations      # *.sql appliqués dans l'ordre des noms (ou database_url: postgres://...)
targets: [18, 19]           # versions PostgreSQL que le code doit supporter
uuid: std                   # std = uuid.UUID, bytes = [16]byte
date: qt                    # qt = qt.Date, stdlib = time.Time
ids: int                    # string = IDs opaques typés (voir §10.2)
exclude: [audit_log]        # tables ignorées
overrides:                  # type PostgreSQL -> type Go
  numeric:
    type: github.com/shopspring/decimal.Decimal
    family: num
json_types:                 # colonne json/jsonb -> votre struct
  users.settings: example.com/app/model.Settings
extensions: [pg_trgm, hstore, ltree, citext]   # paquets d'extension typés
```

Les clés inconnues sont des erreurs. `targets: [16, 17, 18, 19]` est valide : une construction trop récente pour la plus ancienne cible est refusée (§11.3).

### 2.4 Ce qui est généré

Pour chaque table, par exemple `users` :

- un symbole de table `Users` avec une colonne typée par champ : `Users.ID` (`NumCol[int64]`), `Users.Email` (`TextCol[string]`), `Users.Nickname` (`TextCol[qt.Null[string]]`), `Users.CreatedAt` (`TimeCol[time.Time]`) ;
- `Users.As("u")` pour un alias (jointures sur soi-même, sous-requêtes corrélées) ;
- une struct de ligne `User` avec des tags `db:"..."` et `ScanTargets()` (lecture sans réflexion) ;
- un type d'insertion : `NewUserInsert(email)` prend exactement les colonnes sans valeur par défaut, puis des setters chaînés (`.Tier("pro")`, `.Nickname(qt.Some("ada"))`) ;
- un patch `UserPatch`, fait de `qt.Opt` : seuls les champs renseignés sont écrits ;
- les contraintes (`UsersUsersPkey`, pour `ON CONFLICT ON CONSTRAINT`) et les clés étrangères (`Orders.FKOrdersUserIDFkey(Users)`).

Plus, pour le schéma entier : les enums (type Go + constantes), les fonctions scalaires et procédures typées, et `register.go` (spécification du schéma pour la vérification au démarrage).

## 3. Se connecter

```go
import (
    "example.com/qlx/pgxexec"
    q "github.com/noobmaisfier/qlx"
    "example.com/qlx/qt"
)

client, err := pgxexec.Connect(ctx, os.Getenv("DATABASE_URL"), pgxexec.ConnectOptions{
    Spec:      &db.Spec,                // vérifie la version du serveur contre targets
    MinServer: 18,
    OnAhead: func(server int, targets []int) {
        slog.Warn("serveur plus récent que le code généré", "server", server, "targets", targets)
    },
})
if err != nil { return err }
defer client.Close()
```

`Connect` crée le pool pgx, enregistre les codecs de plages, détecte la version du serveur (`client.Dialect`) et prépare le cache de formes. Chaque requête est rendue pour la version réellement en cours : une construction plus récente que le serveur échoue avant tout appel réseau, avec `ErrUnsupportedByServer`.

| Champ de `ConnectOptions` | Rôle |
| --- | --- |
| `Mode` | stratégie de statements pgx (par défaut avec cache) |
| `Tracer` | observe chaque statement (nom, empreinte, lignes, durée) |
| `AfterConnect` | vos propres enregistrements de types, après ceux de la bibliothèque |
| `MinServer` | version majeure minimale ; `Connect` échoue sinon |
| `Spec` | spécification générée ; compare la version du serveur à `targets` |
| `OnAhead` | appelé si le serveur est plus récent que toutes les cibles |
| `Shapes` | remplace le cache de formes global pour ce client |

`client.Pool` est le `pgxpool.Pool` ; `client.DB()` est l'interface `Querier` utilisée par les fonctions de paquet (`pgxexec.All(ctx, tx, ...)` accepte aussi une transaction).

### 3.1 Serverless et poolers en mode transaction

Une fonction conserve son processus entre les invocations, mais quatre choses
changent.

**Mode des statements.** Le défaut `CacheStatements` prépare des statements
nommés une fois par connexion. Derrière un pooler en mode transaction
(PgBouncer, Supavisor, le pooler Neon), la connexion serveur change entre deux
statements, et un scale-to-zero ou un redémarrage du serveur supprime les
statements préparés. Utilisez `Mode: pgxexec.CacheDescribe` : il envoie des
statements anonymes et met leur description en cache, le mode que le paquet
documente comme sûr en transaction pooling. `pgxexec.Simple` est le dernier
recours, pour les poolers qui ne supportent rien d'autre ; il envoie les
paramètres en protocole texte, où la forme texte de certains types diffère de
la forme binaire.

**Taille du pool.** `Connect` laisse les défauts de pgxpool, dimensionnés pour
un serveur : `pool_max_conns = max(4, NumCPU)`. Une fonction qui traite une
requête à la fois n'a besoin que d'une connexion par instance ; mille instances
concurrentes ouvriraient sinon des milliers de connexions. Réglez-la dans le
DSN :

```text
postgres://...?pool_max_conns=1&pool_min_conns=0&pool_max_conn_idle_time=5m&statement_timeout=5s
```

**Un client par processus.** `Connect` exécute `SHOW server_version_num` ;
l'appeler à chaque requête jette le pool et le cache de formes. Créez le client
une fois, au démarrage ou paresseusement avec `sync.Once`, et ne l'appelez pas
`Close` à la fin d'une requête. Après un gel de l'instance, une connexion du
pool peut être morte à l'invocation suivante : pgxpool l'écarte après le
premier échec, et `CacheDescribe` évite l'erreur « prepared statement does not
exist » qu'un cache de statements nommés peut renvoyer après un redémarrage du
serveur.

**Schéma, migrations, ids.** Exécutez `VerifySchema` une fois au cold start sur
les tables utilisées par la fonction, pas à chaque requête (c'est une requête
catalogue), et lancez les migrations en dehors de la fonction, pour que des
instances concurrentes ne se disputent pas le DDL. Quand le schéma utilise
`ids: string`, chaque instance doit appeler `qt.SetIDKey` avec le même secret,
lu depuis l'environnement ou un gestionnaire de secrets : une clé par instance
rend un id émis par une instance illisible par une autre, et une rotation de
clé invalide tous les ids déjà distribués.

Le cache de formes, les caches pgx et le registre de requêtes vivent dans le
processus et ne sont pas partagés entre instances. Le plafond du cache (32 768
formes par défaut, 1 024 par shard) n'est pas préalloué : un statement court
coûte environ 235 octets une fois stocké, donc un programme qui utilise
quelques centaines de formes ne paie que celles-là, et le plafond complet coûte
environ 8 à 15 Mo. `LISTEN`/`NOTIFY` exige une connexion qui reste ouverte :
préférez du polling ou une file quand les instances passent à zéro.

## 4. Lire : `SELECT`

Les builders sont **immuables** : toujours réassigner le résultat (`sel = sel.Where(...)`). Oublier est signalé par l'analyseur (V001).

### 4.1 Le cas simple

{{ex:select-basic}}

`Limit` et `Offset` sont des paramètres (`$2`, `$3`), pas des constantes : une page 1 et une page 7 partagent la même forme.

### 4.2 Filtrer

Règle de nommage importante : `Eq(v)` prend une **valeur** Go (liée en paramètre), `EqX(expr)` prend une **expression** (colonne, fonction, sous-requête). Go ne surcharge pas, donc les deux existent partout : `Gt`/`GtX`, `Lt`/`LtX`, `Gte`/`GteX`...

{{ex:where-operators}}

`Where(a, b, c)` combine avec `AND`. Les autres prédicats : `Ne`, `Gt`, `Gte`, `Lt`, `Lte`, `Between`, `NotBetween`, `BetweenSymmetric`, `In`, `NotIn`, `Like`, `NotLike`, `ILike`, `NotILike`, `SimilarTo`, `LikeEscape`, `IsNull`, `IsNotNull`, `IsDistinctFrom`, `IsNotDistinctFrom`, ainsi que `StartsWith`, `HasPrefix`, `Contains`, `ContainsFold` sur le texte.

Combiner avec `q.And`, `q.Or`, `q.Not` (les parenthèses sont ajoutées là où il faut) :

{{ex:where-or-not}}

Comparer deux colonnes avec les variantes `X` :

{{ex:compare-expressions}}

Une liste déjà en main se passe avec `col.Any(slice)` : un seul paramètre tableau, donc **une seule forme** quelle que soit la longueur (`In(a, b, c)` rend la même chose ; une liste vide donne un prédicat constamment faux).

{{ex:where-any-slice}}

Sur une colonne nullable, un `None` dans la liste veut dire NULL : `Users.Nickname.In(qt.Some("a"), qt.None[string]())` rend `("nickname" = ANY($1) OR "nickname" IS NULL)`, parce que le `= ANY` de SQL avec un élément NULL ne trouve jamais une ligne NULL. `NotAll` fait l'inverse : un `None` ajoute `AND "nickname" IS NOT NULL`. Sans `None`, les règles habituelles de SQL s'appliquent (une ligne NULL n'est ni dans la liste ni hors de la liste).

### 4.3 Conditions dynamiques

Deux outils : un `if` Go ordinaire, et les prédicats optionnels `EqIf(qt.Opt[T])` qui disparaissent quand la valeur est absente.

{{ex:where-dynamic}}

Ici `Balance.EqIf(minBalance)` n'a rien ajouté. Une requête construite par morceaux produit quelques formes différentes, chacune rendue une seule fois (§8).

Les autres comparaisons ont leur variante optionnelle : `NeIf`, `InIf`, `IsNullIf`, `GtIf`, `GteIf`, `LtIf`, `LteIf`, `BetweenIf` (bornes indépendantes) et, sur le texte, `ContainsIf`, `ContainsFoldIf`, `HasPrefixIf`, `LikeIf`, `ILikeIf`. Une chaîne vide compte pour absente dans les recherches texte. `InIf` avec une liste fournie mais vide donne `FALSE`, comme `In`. `qlx.When(opt, func(v T) Pred)` couvre le reste.

```go
type Filter struct {
    Tier      qt.Opt[string]
    MinSpent  qt.Opt[int64]
    Since     qt.Opt[time.Time]
    Search    qt.Opt[string]
}

sel.Where(
    Users.Tier.EqIf(f.Tier),
    Users.Balance.GteIf(f.MinSpent),
    Users.CreatedAt.GteIf(f.Since),
    Users.Email.ContainsFoldIf(f.Search),
)
```

Chaque combinaison de filtres présents est une forme distincte (2^n pour n filtres) : pour beaucoup de filtres indépendants, surveillez `ShapeCache.OnThrash`.

La condition vient avec `.On(pred)` (combinez avec `q.And`). Avec une clé étrangère générée, `OnFK` écrit la condition pour vous : renommer une colonne casse la compilation, pas la requête.

### 4.5 Agrégats, `GROUP BY`, `HAVING`

{{ex:aggregates}}

Fonctions : `CountAll`, `Count`, `CountDistinct`, `Sum` (petits entiers), `SumBig` (`bigint`), `SumFloat`, `Avg`, `AvgFloat`, `Min`, `Max`, `StringAgg`, `ArrayAgg`, `BoolAnd`, `BoolOr`..., plus les agrégats générés du catalogue (`num.StddevInt8`, ...). Les résultats sont nullables quand le SQL peut renvoyer `NULL` (`Sum` sur zéro ligne), pas pour `count`.

Modificateurs : `Distinct`, `Filter(pred)`, `OrderBy(...)` à l'intérieur de l'agrégat.

{{ex:aggregate-modifiers}}

### 4.6 Fonctions de fenêtre

{{ex:window}}

`q.Window()` décrit la fenêtre (`PartitionBy`, `OrderBy`, `Rows`, `Range`, `Groups`, exclusions) ; `.Over(w)` l'applique à une fonction de fenêtre (`RowNumber`, `Rank`, `DenseRank`, `PercentRank`, `CumeDist`, `Ntile`, `Lag`, `Lead`, `FirstValue`, `LastValue`, `NthValue`) ou à un agrégat. Fenêtre nommée : `q.NewWindow("w", spec)` puis `.Windows(w)`. Sur PostgreSQL 19, `Lag(...).IgnoreNulls()` rend `IGNORE NULLS` ; sur 18 c'est une erreur de rendu qui nomme la version.

### 4.7 CTE et récursion

{{ex:cte}}

Une CTE s'utilise avec `.With(cte)` ; ses colonnes se lisent par `q.Ref` / `q.RefNum` / `q.RefText` avec un `q.NewField[T]("nom")` qui porte le type. `Materialized()` et `NotMaterialized()` règlent la matérialisation. Les CTE récursives :

```go
tree := q.Recursive("tree", anchorQuery, func(self q.CTE) q.Query { return stepQuery(self) }).
    SearchDepthFirst("ord", byColumns...) // WITH RECURSIVE ... SEARCH DEPTH FIRST ... CYCLE
```

`SearchBreadthFirst` et `Cycle(marque, chemin, colonnes...)` complètent les options.

{{ex:subquery-exists}}

{{ex:subquery-in}}

### 4.9 Opérations ensemblistes

{{ex:set-operations}}

`Union`, `UnionAll`, `Intersect`, `IntersectAll`, `Except`, `ExceptAll` existent en fonctions (`q.UnionAll(a, b)`) et en méthodes. `ByName` aligne les colonnes par nom.

### 4.10 Expressions : `CASE`, `COALESCE`, arithmétique

{{ex:case-coalesce}}

`Case[T]().When(pred, v)...Else(v)` rend un résultat non nul ; sans `Else`, `End()` rend un `qt.Null[T]`. `Coalesce` retire la nullabilité. Autres : `q.NullIf`, `q.Greatest`, `q.Least`.

{{ex:arithmetic-functions}}

Les opérations arithmétiques sont typées : `Add`, `Sub`, `Mul`, `Div`, `Mod`, `Neg`, `Abs`. Les fonctions texte courantes sont des méthodes (`Upper`, `Lower`, `Trim`, `Replace`, `Reverse`, `Length`...). Pour toutes les autres fonctions de PostgreSQL, voir §11 (`pg.Length`, `text.Concat`, ...).

### 4.11 Conversions de type

{{ex:cast}}

`q.PgText`, `q.PgInt4`, `q.PgInt8`, `q.PgNumeric`, `q.PgDate`, `q.PgTimestamptz`, `q.PgJSONB`, ... sont les types cibles. Pour un type d'enum ou de composite défini par vous : `q.NewPgType[T]("schema", "nom")`.

### 4.12 Verrouillage de lignes

{{ex:locking}}

`ForUpdate`, `ForNoKeyUpdate`, `ForShare`, `ForKeyShare`, avec `Of(table...)`, `NoWait` ou `SkipLocked`. C'est le motif classique d'une file de travail : plusieurs workers prennent chacun des lignes différentes.

### 4.13 Fonctions qui renvoient des lignes

{{ex:generate-series}}

Une fonction « set-returning » devient une source de lignes (`TableFunc`) : on donne l'alias et les colonnes avec leur type (`As("s", x)`), et `q.RefNum(s, x)` lit la colonne. `WithOrdinality(col)` ajoute `WITH ORDINALITY`. `q.Unnest`, `q.Unnest2`, `q.GenerateSeries*` et les fonctions JSON (`JSONBArrayElements`...) sont écrites à la main ; les autres sont générées (§11).

### 4.14 `EXPLAIN`

{{ex:explain}}

Options : `q.Analyze`, `q.Verbose`, `q.Buffers`, `q.FormatJSON`, `q.IO` et `q.PlanAdvice` (PostgreSQL 19). `Explain` existe aussi sur `Update`, `Delete`, `Insert` et `Merge`.

### 4.15 Nommer une requête

{{ex:tagged}}

### 5.1 `INSERT`

Une ligne, avec `RETURNING` :

{{ex:insert-row}}

{{ex:insert-rows}}

À partir d'un `SELECT` :

{{ex:insert-select}}

Une colonne `NOT NULL` sans valeur par défaut oubliée dans un `INSERT` ne se rend pas (et l'analyseur le dit avant, V008). Le type d'insertion généré rend l'oubli impossible à **compiler** :

```go
ins := q.InsertInto(Users).Values(
    NewUserInsert("ada@example.com").   // colonnes obligatoires : paramètres de la fonction
        Tier("pro").                    // colonnes facultatives : setters
        Nickname(qt.Some("ada")))
```

`DefaultValues()`, `OverridingSystemValue()` et `OverridingUserValue()` couvrent les colonnes d'identité.

Les champs facultatifs d'un corps de requête s'écrivent avec `ToIf(opt)` plutôt qu'un `if` par champ : un `qt.Opt` non renseigné retire l'affectation (la colonne n'est pas dans l'`INSERT`, intacte dans l'`UPDATE`). `ToOrDefault(opt)` écrit `DEFAULT` à la place, ce qui garde alignées les lignes d'un `INSERT` multiple ; `ToDefault()` le fait toujours. Le détail et les règles sont dans [le guide des DTO](dtos.md).

```go
q.InsertInto(Users).Row(
    Users.Email.To(r.Email),
    Users.Tier.ToIf(r.Tier), // r.Tier est un qt.Opt[string] : absent, la colonne prend son DEFAULT
)
```

### 5.3 `UPDATE`

{{ex:update}}

Mettre un champ nullable à `NULL` : `Users.Nickname.ToNull()`, la forme courte de `Users.Nickname.To(qt.None[string]())` ; elle couvre aussi les colonnes nullables qui ne sont pas un `qt.Null` (tableaux, `bytea`, plages). Go ne permet pas de réserver une méthode à certains types de colonnes : `ToNull()` compile donc aussi sur une colonne `NOT NULL`, le serveur la refuse (23502) et l'analyseur la signale avant (V030). Un `UPDATE` sans `Where` ni `All()` ne se rend pas :

```go

```

### 5.5 `MERGE`

{{ex:merge}}

Les formes `WhenMatched`, `WhenNotMatched`, `WhenNotMatchedBySource` acceptent une condition et se terminent par `ThenUpdate`, `ThenInsert`, `ThenDelete` ou `ThenDoNothing`. `q.MergeAction()` donne l'action dans `RETURNING`.

### 5.6 `RETURNING OLD / NEW` (PostgreSQL 18)

`Colonne.Old()` et `Colonne.New()` lisent la valeur avant et après dans `RETURNING`. Avec une cible 17 ou moins, c'est une erreur de rendu qui nomme la version. `Old()` et `New()` ne sont acceptés que dans `RETURNING` (utiliser ailleurs ne compile pas).

{{ex:returning-old-new}}

## 6. Nullabilité, options et patchs

Une colonne nullable est un `qt.Null[T]` : `qt.Some(v)`, `qt.None[T]()`, `.Valid`, `.V`. Les pointeurs ne sont pas proposés : un `*T` ne distingue pas « NULL » de « non chargé ».

```go
var nick qt.Null[string]
nick = qt.Some("ada")
if nick.Valid { fmt.Println(nick.V) }
```

Pour une condition ou un patch partiel, `qt.Opt[T]` (`qt.Of(v)`, `qt.Unset[T]()`, `.Set`, `.V`) distingue « ne pas toucher » de « mettre à NULL » :

| Valeur | Dans un patch | Dans `EqIf` |
| --- | --- | --- |
| `qt.Unset[string]()` | champ ignoré | prédicat absent |
| `qt.Of("x")` | `SET col = 'x'` | `col = 'x'` |
| `qt.Of(qt.None[string]())` (colonne nullable) | `SET col = NULL` | `col IS NOT DISTINCT FROM NULL` n'existe pas : utilisez `IsNull()` |

Les résultats de fonctions respectent la nullabilité SQL : `Coalesce(col, valeur)` renvoie un type non nul ; `Scalar(sub, col)` et `Case ... End()` renvoient un `qt.Null[T]`. « Strict » (la fonction renvoie `NULL` si un argument l'est) n'est pas « non nul » : `jsonb ->> 'clé'` d'une clé absente est `NULL`, donc ces wrappers renvoient `qt.Null`.

## 7. Exécuter et lire les résultats

```go
type UserRow struct {
    ID    int64  `db:"id"`
    Email string `db:"email"`
}

rows, err := client.All[UserRow](ctx, sel)          // []UserRow
one,  err := client.One[UserRow](ctx, sel)          // exactement une ligne, sinon pgx.ErrNoRows / pgx.ErrTooManyRows
opt,  err := client.Maybe[UserRow](ctx, sel)        // qt.Opt[UserRow] : zéro ou une ligne
for row, err := range client.Each[UserRow](ctx, sel) { ... } // flux, sans tout charger
tag,  err := client.Exec(ctx, ins)                  // sans lignes retournées : pgconn.CommandTag
```

Ce que `R` peut être :

| `R` | Lecture |
| --- | --- |
| un scalaire (`int64`, `string`, `qt.Null[T]`...) | une seule colonne sélectionnée |
| `q.Tuple1[A]` ... `q.Tuple8[...]` | colonnes par position, sans réflexion |
| une struct avec `ScanTargets()` | par position, sans réflexion (structs générées, ou `qlx rows`) |
| une struct avec tags `db` | par nom de colonne, via un plan mis en cache |

```go
// Une colonne, un scalaire
n, err := client.One[int64](ctx, q.Select(q.CountAll()).From(Users))

// Plusieurs colonnes sans déclarer de struct
t, err := client.One[q.Tuple2[int64, string]](ctx,
    q.Select(Users.ID, Users.Email).
        From(Users).
        Where(Users.ID.Eq(7)))
fmt.Println(t.V1, t.V2)
```

Pour qu'une struct à vous lise sans réflexion, marquez-la et lancez `qlx rows` :

```go
//qlx:row
type UserSummary struct {
    ID    int64
    Email string
    Posts int64 `qlx:"-"` // champ ignoré : pas une colonne sélectionnée
}
```

Les champs suivent l'ordre des colonnes sélectionnées. Les champs embarqués et les types génériques sont refusés (l'ordre serait une supposition). Une struct sans `ScanTargets` est lue par nom, et une colonne sans champ correspondant est une erreur nette, pas une lecture silencieuse de travers.

> Les méthodes `client.All[R]` etc. utilisent les méthodes génériques de Go 1.27. Les fonctions de paquet `pgxexec.All[R](ctx, db, stmt)` existent aussi et acceptent un `pgx.Tx`.

### Erreurs

Les erreurs PostgreSQL se testent sans comparer de chaînes :

```go
_, err := client.Exec(ctx, ins)
switch {
case pgxexec.IsUnique(err, "users_email_key"):   // 23505 sur cette contrainte
    return ErrEmailTaken
case pgxexec.IsForeignKey(err, ""):              // 23503 (n'importe quelle contrainte)
    return ErrUnknownUser
case pgxexec.IsNotNull(err, "email"):            // 23502 sur cette colonne
case pgxexec.IsCheck(err, ""):                   // 23514
case pgxexec.IsSerialization(err):               // 40001 ou 40P01 : à réessayer (voir InTx)
}
if pgxexec.IsNoRows(err) { /* One sur un résultat vide */ }
```

### Vérifier le type de résultat

Le type `R` de `client.One[R]` n'est pas lié par le compilateur aux colonnes du `Select`. Trois filets, du plus tôt au plus tard :

- l'analyseur (V018) compare `R` aux colonnes quand le `Select` est écrit dans le source : nombre, types, nullabilité, et ordre des champs pour une struct à `ScanTargets` ;
- `pgxexec.VerifyRow[R](ctx, conn, st)` dans un test : prépare la requête sur un vrai serveur et vérifie que chaque colonne a un plan de lecture pgx vers sa destination, sans exécuter la requête ;
- à la première exécution : le plan par nom échoue avec « has no field for column x » ou « field T.F has no column ».

```go
func TestRowsMatch(t *testing.T) {
    st, _ := client.Render(userByID)
    if err := pgxexec.VerifyRow[UserRow](ctx, conn, st); err != nil { t.Fatal(err) }
}
```

Aucun ne voit un `NULL` réel : une colonne nullable lue dans un champ non nullable n'échoue que sur la ligne qui contient le `NULL` ; l'analyseur la signale quand le `Select` est lisible, sinon utilisez `qt.Null[T]` ou un pointeur.

Les erreurs du moteur de requêtes se testent avec `errors.Is` : `qlx.ErrUnsupportedByServer`, `qlx.ErrShape` (requête mal formée : `UPDATE` sans `Where`, colonne obligatoire oubliée...), `qlx.ErrInvalidIdent`.

## 8. Performance : mode normal et mode statique

### 8.1 Le mode normal

QLX a deux modes : le **mode normal**, par défaut, et le **mode statique**, pour
les chemins les plus chauds.

Vous n'avez rien à faire. La première fois qu'une *forme* de requête passe (même structure, valeurs différentes), elle est rendue et validée ; ensuite, un hachage de la forme retrouve le SQL et seules les valeurs sont collectées. Environ 1 à 4 µs et 11 à 32 allocations pour une requête de taille courante, contre 7 µs et 70 pour un rendu complet.

```go
client.Shapes.Stats()   // Hits, Misses, Evictions, Size
```

Pour garder le nombre de formes borné : passez les listes avec `col.Any(slice)` (une forme pour toute longueur). Varier la structure elle-même est permis et correct : un rapport construit par l'utilisateur ou un ensemble de colonnes dynamique est rendu une fois par forme, puis réutilisé. Quand `Evictions` grimpe, augmentez le plafond pour ce client (`Shapes: qlx.NewShapeCache(n)`) ou rendez une fois les formes les plus chaudes avec `client.Render`.

### 8.2 Le mode statique

Pour les chemins les plus chauds, rendez une fois et liez par appel (60 à 70 ns, 1 allocation) :

```go
id := q.NewParam[int64]()
var userByID = q.Register("user_by_id", q.Tagged("user_by_id",
    q.Select(Users.ID, Users.Email).From(Users).Where(Users.ID.EqX(id))))

st, _ := client.Render(userByID)                          // au démarrage
row, err := client.One[UserRow](ctx, st, id.Bind(42))     // aucun parcours d'AST
```

Des handles typés évitent de répéter les liaisons : `pgxexec.NewStatic0..4[R](dialect, stmt, params...)` (`params` sont les `q.Param[T]` du statement) donne un objet avec `All`, `One`, `Maybe`, `Each`, `Exec` dont les arguments sont typés :

```go
byID := pgxexec.NewStatic1[UserRow](
    client.Dialect,
    q.Select(Users.ID, Users.Email).From(Users).Where(Users.ID.EqX(id)),
    id)
row, err := byID.One(ctx, client.DB(), 42)   // 42 est un int64 vérifié à la compilation
```

`Tagged` préfixe le SQL de `/* qlx: user_by_id */`. `Register` nomme le statement pour les snapshots, `qtest.Dump` et `qlx prepare`, et doit être appelé au niveau du paquet avec un nom constant (V003, V005).

## 9. Transactions, pipelines, COPY, LISTEN

### 9.1 Transactions avec reprise

```go
err := pgxexec.InTx(ctx, client.Pool, pgx.TxOptions{IsoLevel: pgx.Serializable},
    pgxexec.Retry{Attempts: 5},
    func(ctx context.Context, tx pgx.Tx) error {
        // Peut s'exécuter plusieurs fois en cas de conflit de sérialisation ou de deadlock :
        // aucun effet de bord hors de la transaction.
        // balanceStmt et debitStmt sont des qlx.Stmt déjà rendus (client.Render)
        bal, err := pgxexec.One[int64](ctx, tx, balanceStmt, id.Bind(7))
        if err != nil { return err }
        if bal < 100 { return ErrInsufficient }
        _, err = pgxexec.Exec(ctx, tx, debitStmt, id.Bind(7))
        return err
    })
```

`Retry{Attempts, Base, OnRetry}` : nombre d'essais (5 par défaut), premier délai (10 ms, doublé avec gigue), et un rappel pour compter les reprises dans vos métriques. Seuls `40001` et `40P01` sont rejoués.

### 9.2 Pipeline : plusieurs requêtes, un aller-retour

```go
// getUser et listPosts sont des qlx.Stmt rendus au démarrage (client.Render)
var p pgxexec.Pipeline
user  := pgxexec.PipeOne[UserRow](&p, getUser, id.Bind(7))
posts := pgxexec.PipeAll[PostRow](&p, listPosts, id.Bind(7))
if err := p.Run(ctx, client.Pool); err != nil { return err }
u, _ := user.Get()     // typé ; ErrNotRun avant Run
ps, _ := posts.Get()
```

Les types lus par un pipeline ont besoin de `ScanTargets` (structs générées, `qlx rows`, ou `q.TupleN`). `BatchAll` / `BatchOne` lisent les résultats d'un `pgx.Batch` classique, et `pgxexec.Batch` (`Queue(stmt, binds...)`, `Send`) en construit un.

### 9.3 `COPY` binaire

```go
n, err := pgxexec.CopyIn(ctx, client.Pool,
    q.CopyIn(Users, Users.Email, Users.Balance),
    pgxexec.CopyRows([][]any{{"a@example.com", int64(0)}, {"b@example.com", int64(10)}}))
```

C'est le chemin le plus rapide pour charger beaucoup de lignes. `CopyQueryOut` et `CopyTableOut` couvrent `COPY ... TO`.

`COPY` n'accepte pas de paramètres : `CopyQueryOut(...)` et `CopyIn(...).Where(...)` refusent une instruction qui en porte (`ErrParams`). `.InlineArgs()` écrit à la place les arguments dans le SQL, comme littéraux, et n'accepte que les valeurs dont le texte est fabriqué par le type seul : entiers, booléens, flottants, `time.Time`, uuid, octets, NULL, tranches de ces types, et chaînes en ASCII imprimable sans apostrophe ni antislash. Toute autre valeur, et tout paramètre lié plus tard avec `Bind`, donne une erreur `ErrParams` : la chaîne est refusée, jamais échappée.

```go
st, _ := client.Render(q.CopyQueryOut(
    q.Select(Orders.ID, Orders.Total).From(Orders).Where(Orders.Status.Eq("paid"), Orders.CreatedAt.Gte(since)),
).InlineArgs().With(q.WithFormat(q.CopyCSV)))
```

Chaque valeur distincte est une instruction distincte : acceptable pour `COPY`, et c'est pourquoi ce n'est pas le comportement par défaut.

### 9.3b `INSERT` en lots

Quand il faut `ON CONFLICT` ou `RETURNING`, que `COPY` ne sait pas faire, `InsertMany` découpe les lignes en instructions qui respectent la limite de 65 535 paramètres du protocole :

```go
n, err := pgxexec.InsertMany(ctx, client.Pool, client.Dialect,
    q.InsertInto(Users).OnConflict(Users.Email).DoNothing(),
    rows, pgxexec.BulkOptions{})   // rows is a []q.RowAssigner: the generated insert types

ids, err := pgxexec.InsertManyReturning[int64](ctx, client.Pool, client.Dialect,
    q.InsertInto(Users).Returning(Users.ID), rows, pgxexec.BulkOptions{})
```

Avec un pool ou une connexion et plus d'une instruction, tout s'exécute dans une transaction : un échec ne laisse rien. Avec un `pgx.Tx`, les instructions rejoignent la vôtre. Une ligne coûte un paramètre par colonne ; abaissez `MaxParams` si des `ToX` portent des arguments. Le découpage seul est `InsertQuery.Chunks(rows, maxParams)`. La dernière instruction, plus courte, est une forme de plus dans le cache.

### 9.4 `LISTEN` / `NOTIFY`

```go
ch, _ := pgxexec.NewChannel("jobs")
for n := range pgxexec.ListenChan(ctx, client.Pool, pgxexec.ListenOptions{}, ch) {
    handle(n.Payload)
}
// côté émetteur : client.Exec(ctx, q.Notify("jobs", "payload"))
```

La connexion revient au pool avec `UNLISTEN *`, et se rétablit avec un délai croissant en cas de coupure. Les notifications envoyées pendant la coupure sont perdues : utilisez `OnReconnect` pour resynchroniser.

### 9.5 Multi-tenant (RLS)

```go
st, err := client.Render(q.SetConfig("app.tenant", tenantID, true)) // tenantID : string
if err != nil { return err }
_, err = pgxexec.Exec(ctx, tx, st) // tx : le pgx.Tx de la transaction en cours
```

`set_config` avec une valeur **liée** : l'identifiant du tenant n'est jamais concaténé dans le SQL.

{{ex:set-config}}

Autres commandes utilitaires, rendues et exécutées comme des requêtes : `q.Listen`, `q.Notify`, `q.SetRole`, `q.Reset`, `q.Show`, `q.DiscardPlans`, `q.SetConstraints`, `q.Savepoint`, `q.Vacuum`, `q.Truncate`, `q.LockTable`, `q.RefreshMaterializedView`, `q.Reindex`, `q.Cluster`, `q.Grant`, `q.Revoke`.

## 10. Mappings et types

Quatre correspondances décident de ce que vous écrivez et de ce que vous lisez. Les comprendre évite l'essentiel des erreurs à l'exécution.

| Correspondance | Règle en une phrase | Où |
| --- | --- | --- |
| Noms : schéma SQL → code Go | `snake_case` devient `CamelCase`, avec initialismes (`user_id` → `UserID`) | §10.6 |
| Types : type PostgreSQL → type Go | table ci-dessous ; surcharge par `overrides` ; un type inconnu devient `string` avec un avertissement | table, §10.7 |
| Nullabilité : `NULL` → Go | colonne nullable = `qt.Null[T]` ; côté optionnel d'un `LEFT JOIN` = à marquer vous-même | §10.8 |
| Valeurs : Go → paramètres SQL | toujours un `$n` lié, jamais du texte collé ; `q.Val` ajoute le type | §10.9 |
| Lignes : colonnes d'un résultat → `R` | par position (`ScanTargets`), par nom (tags `db`), ou un scalaire | §10.10 |

La table qui suit est la correspondance de types. §10.11 dit comment vérifier tout cela avant la production.

| PostgreSQL | Go |
| --- | --- |
| `smallint`, `integer`, `bigint` | `int16`, `int32`, `int64` |
| `real`, `double precision` | `float32`, `float64` |
| `numeric` | `qt.Numeric` (ou votre type via `overrides`) |
| `text`, `varchar`, `char(n)` | `string` |
| `"char"` (un octet interne) | `qt.Char` |
| `boolean` | `bool` |
| `bytea` | `[]byte` |
| `uuid` | `uuid.UUID` (ou `[16]byte` avec `uuid: bytes`) |
| `date` | `qt.Date` (ou `time.Time` avec `date: stdlib`) |
| `time`, `timetz` | `qt.TimeOfDay`, `qt.TimeTZ` |
| `timestamp` | `qt.LocalTime` |
| `timestamptz` | `time.Time` |
| `interval` | `qt.Interval` |
| `json`, `jsonb` | `qt.JSONB[T]` (T : `json.RawMessage` ou votre struct) |
| `inet`, `cidr` | `netip.Addr`, `netip.Prefix` |
| `int4range`, `daterange`, `tstzrange`... | `qt.Range[T]` |
| `int4multirange`... | `qt.Multirange[T]` |
| `T[]` | `[]T` |
| enum | type Go généré + constantes |
| clé primaire entière avec `ids: string` | `qt.ID[Espace]` |
| `tsvector`, `tsquery`, `bit`, `point`, `box`, `money`, `pg_lsn`, `xml`, `regclass`, `jsonpath`... | chaînes nommées de `qt` (format texte de PostgreSQL) |
| colonne nullable de n'importe quel type | `qt.Null[T]` |

Un type texte (`qt.TSVector`, `qt.Point`, ...) ne se convertit pas implicitement : une valeur d'un type ne passe pas pour un autre. Convertissez avec la bibliothèque de votre choix aux frontières.

### 10.1 Dates et heures

```go
d := qt.DateOf(2026, time.October, 28)
d.AddDays(30).Before(qt.Today(time.UTC))
d.Time()                                  // minuit UTC, si un time.Time est nécessaire
qt.TimeOfDayOf(13, 45, 0, 0).On(d, loc)   // combine en time.Time
Posts.PostedOn.Gte(d)                     // une colonne date se compare à qt.Date
```

`qt.Date` compte des jours depuis une époque et supporte `infinity`/`-infinity` ; `qt.TimeOfDay` compte des microsecondes depuis minuit. `CURRENT_DATE` rend un `qt.Date` (`q.CurrentDate()`), `q.CurrentTime()` un `qt.TimeTZ`, `q.LocalTime()` un `qt.TimeOfDay`, `q.Now()` un `time.Time`.

### 10.2 IDs opaques

```yaml
ids: string
```

```go
qt.MustSetIDKey(secret)   // une fois au démarrage : 16+ octets aléatoires, stables

p, _ := client.One[blog.Post](ctx, query)
json.Marshal(p)           // {"id":"7mQp3VxK9cE","author_id":"Ck4RtYw2nHa",...}

id, err := qt.ParseID[blog.PostsIDSpace](r.PathValue("id"))   // faute ou chaîne forgée : qt.ErrBadID
Posts.ID.Eq(id)           // la base compare toujours des entiers
Posts.AuthorID.Eq(id)     // ne compile pas : un ID d'auteur n'est pas un ID d'article
```

Toute clé primaire entière à une colonne, et toute clé étrangère qui la référence, reçoit le type d'ID de sa table. En base, rien ne change : jointures, index et tris restent des entiers. Du côté Go, la conversion est automatique via `encoding.TextMarshaler` (JSON, routeurs, `fmt`, `slog`). 11 caractères base58, longueur fixe, environ 90 ns, sans allocation.

C'est de l'obfuscation, pas du chiffrement : gardez vos contrôles d'autorisation. Changer la clé change tous les textes déjà distribués (jamais les entiers). Domaine : 0 à 2^48 − 1 (`qt.ErrIDRange` au-delà). Voir [limits](limits.md).

### 10.3 JSON

Une colonne `jsonb` est un `qt.JSONB[T]`. Avec `json_types` dans `qlx.yaml`, `T` est votre struct :

```yaml
json_types:
  users.settings: example.com/app/model.Settings
```

```go
type Settings struct{ Theme string `json:"theme"` }
// Users.Settings est alors une colonne qt.JSONB[model.Settings] : lue et écrite sans json.Unmarshal manuel.
```

Les constructeurs SQL/JSON ont leurs builders : `q.JSONObject`, `q.JSONArray`, `q.JSONExists`, `q.JSONValue[T]`, `q.JSONQuery`, `q.JSONTable`, `q.JSONParse(text)` (`.WithUniqueKeys()`, PostgreSQL 17), `q.JSONSerialize`, `q.JSONScalar`. Les opérateurs et fonctions `jsonb` sont dans `pgcat/jsonb` : `jsonb.JsonbPathExists(doc, q.Val(qt.JSONPath("$.a[*] ? (@ > 1)")), vars, q.Val(true))`.

### 10.4 Tableaux, plages, enums

- Tableau : `Col[[]string]` ; `ANY($1)` pour tester l'appartenance (`col.Any(slice)`) ; opérateurs dans `pgcat/array`.
- Plages : `qt.Range[T]` (`Lower`, `Upper` en pointeurs, `LowerInc`, `UpperInc`, `Empty`) ; opérateurs et bornes dans `pgcat/ranges`. Un `qt.Range` nul porte `Null: true`.
- Enum : un type Go par enum avec ses constantes, comparable et typé (`Members.Tier.Eq(TierPro)`).

### 10.5 `numeric`

`qt.Numeric` conserve la valeur exacte en texte. Pour une bibliothèque décimale, déclarez l'override :

```yaml
overrides:
  numeric:
    type: github.com/shopspring/decimal.Decimal
    family: num
```

### 10.6 Les noms

Le générateur transforme les noms SQL en identifiants Go exportés :

| SQL | Go | Règle |
| --- | --- | --- |
| `user_id` | `UserID` | mots séparés par `_`, première lettre en capitale, initialismes en majuscules |
| `api_url` | `APIURL` | initialismes reconnus : `id url uuid api ip http https json jsonb html sql xml uri ttl cpu os db tls ssl ssh csv pdf ui` |
| table `users` | `Users` (symbole), `UsersT` (type), `User` (ligne) | la ligne est le singulier : `ies` → `y`, `sses/xes/ches/shes` → sans `es`, `ss/us/is` inchangés, sinon sans `s` final |
| colonne `type` | `Type` | un mot réservé du paquet reçoit le suffixe `Col` ; deux colonnes qui donnent le même nom sont numérotées |
| table en collision | suffixe du schéma, puis `Row` ou un numéro | pour que deux schémas n'écrasent pas un même symbole |

La struct de ligne garde le nom SQL dans ses tags : `ID int64 `db:"id"``, `UserID int64 `db:"user_id"``. C'est ce tag qui sert à la lecture par nom (§10.10), pas le nom Go.

### 10.7 Types : comment un type est choisi

Pour chaque colonne, le générateur essaie dans cet ordre :

1. un `override` pour `schema.type`, puis pour `type` ;
2. un tableau → `[]T` avec le type de l'élément ;
3. un domaine → le type de sa base ;
4. un enum → le type Go généré ;
5. une plage ou multi-plage → `qt.Range[T]` / `qt.Multirange[T]` ;
6. un type natif de la table ci-dessus ;
7. un type d'une extension activée (`extensions:` dans `qlx.yaml`) ;
8. sinon `string`, avec un avertissement à la génération : « add an override or enable its extension pack ». C'est le cas d'un type composite ou d'un type d'extension non activée.

```yaml
overrides:
  numeric:                       # tous les numeric
    type: github.com/shopspring/decimal.Decimal
    family: num
  billing.money_amount:          # un seul type, par schéma.nom
    type: example.com/app/money.Amount
    family: num
```

`family` choisit les opérateurs de la colonne : `num` (`Gt`, `Add`, `Sum`...), `text` (`Like`, `Upper`...), `time` (comparaisons de dates), sinon `col` (égalité, `IN`, `IS NULL`). Un type que vous apportez doit savoir se lire et s'écrire avec pgx (`Scan`/`Value` ou les interfaces de `pgtype`).

Quelques précisions :

- `varchar(n)` et `char(n)` sont des `string` : la longueur n'est pas vérifiée côté Go, la base la vérifiera à l'écriture.
- Pas de types non signés : `oid` est le seul `uint32`.
- `json` et `jsonb` sont les mêmes types Go (`qt.JSONB[T]`) ; `json_types:` choisit `T` par colonne (§10.3).
- `date: stdlib` donne `time.Time` au lieu de `qt.Date` ; `uuid: bytes` donne `[16]byte`.

### 10.8 Nullabilité

Une colonne `NOT NULL` est un `T`. Une colonne nullable est un `qt.Null[T]` (`.Valid`, `.V`, `qt.Some`, `qt.None[T]()`, JSON : `null` ou la valeur). Trois types portent déjà leur « absence » et ne sont pas enveloppés : un tableau (`[]T`, `nil` = `NULL`), `bytea` (`[]byte`, `nil` = `NULL`) et une plage (`qt.Range` a un drapeau `Null`).

Ce que la base ou l'expression décide :

| Expression | Type Go |
| --- | --- |
| colonne `NOT NULL` | `T` |
| `Count`, `CountAll` | `int64` |
| `Sum`, `Avg`, `Max`, `Min`, `ArrayAgg`... | `qt.Null[T]` (aucune ligne = `NULL`) |
| `Coalesce(col, valeur)` | `T` |
| `Scalar(sous-requête, col)`, `Case ... End()` | `qt.Null[T]` |
| fonction « stricte » sur un argument nul | `qt.Null[T]` quand le résultat peut être `NULL` |

**Le piège des jointures externes.** Les colonnes du côté optionnel d'un `LEFT JOIN` (la table jointe), d'un `RIGHT JOIN` (l'autre table) ou des deux côtés d'un `FULL JOIN` sont `NOT NULL` dans le schéma, donc typées `T`, mais valent `NULL` quand aucune ligne ne correspond. Lues dans un `int64`, elles font échouer la lecture de cette ligne (`cannot scan NULL into *int64`), et seulement quand le cas se présente. Deux façons correctes :

{{ex:left-join-nullable}}

`q.Nullable(col)` ne change pas le SQL : il type la valeur `qt.Null[T]`, donc le champ qui la reçoit doit être un `qt.Null[T]` (ou un pointeur). On peut aussi lire la colonne brute dans un champ `qt.Null[T]` : lire un `T` dans un `qt.Null[T]` est toujours permis. L'analyseur (V018) signale une colonne du côté optionnel lue dans un champ qui ne peut pas contenir `NULL`.

Dans le sens inverse, écrire : `qt.None[T]()` donne `NULL`, `qt.Some(v)` donne la valeur ; pour un patch partiel, `qt.Opt[T]` distingue « ne pas toucher » de « mettre à `NULL` » (§6).

### 10.9 Valeurs Go → paramètres

Une valeur Go n'est jamais écrite dans le SQL : elle devient un paramètre `$n` que pgx encode. Les types acceptés sont ceux des colonnes (§10) plus tout ce que pgx sait encoder.

- `Users.Balance.Gt(100)` : `100` est un `int64` vérifié par le compilateur (le type de la colonne), rendu `$3` sans cast : le serveur déduit le type de la comparaison.
- `q.Val(x)` : le paramètre porte son type, rendu `$1::int8`, `$2::text`. Nécessaire quand le serveur n'a rien pour le déduire (une valeur seule dans un `SELECT`, un argument de fonction polymorphe) :

{{ex:param-typing}}

- `q.NewParam[T]()` : paramètre nommé, lié à chaque exécution avec `.Bind(v)` (§8.2).
- `col.Any(slice)` : un seul paramètre tableau pour toute longueur (§4.2).
- `qt.Null` et `qt.Opt` s'écrivent selon §6 ; un `qt.Range` porte ses bornes et son drapeau vide.
- Une valeur d'un type texte de `qt` (`qt.Point`, `qt.TSVector`...) s'envoie au format texte de PostgreSQL ; `qt.JSONB[T]` est sérialisé en JSON.

Les identifiants (noms de table, de colonne, de contrainte) ne sont jamais des paramètres : ils viennent du code généré ; un nom écrit à la main est validé et cité (`q.QuoteIdent`, `ErrInvalidIdent`).

### 10.10 Colonnes de résultat → `R`

Cette section est le résumé ; [Mapping rows to Go types](mapping.md) (en anglais) détaille chaque cas (jointures, données imbriquées, tuples) et la vérification de chaque mapping.

`client.One[R]` lit chaque ligne dans `R` selon trois modes, choisis dans cet ordre :

| Mode | Quand | Règle de correspondance |
| --- | --- | --- |
| Position | `*R` a une méthode `ScanTargets()` : structs générées, `qlx rows`, `q.Tuple1..8` | la colonne *i* va dans le champ *i* de la liste ; nombre de colonnes et de champs identiques |
| Nom | `R` est une struct sans `ScanTargets` | le nom de colonne (en minuscules) est comparé au tag `db`, sinon au nom du champ **mis en minuscules** |
| Scalaire | `R` n'est pas une struct, ou une struct qui est une valeur (`time.Time`, `qt.Null[T]`, `netip.Addr`) lue sur une seule colonne | exactement une colonne |

Les règles de la lecture par nom, qui surprennent le plus :

- Le nom Go n'est **pas** converti en `snake_case` : un champ `UserID` s'appelle `userid`, pas `user_id`. Pour une colonne `user_id`, écrivez `UserID int64 `db:"user_id"``. Les structs générées portent déjà les tags.
- Une colonne sans champ est une erreur : `T has no field for column x (tag a field with db:"x")`. Un champ sans colonne l'est aussi : `field T.F has no column in the result (tag it db:"-" to skip it)`. Il n'y a ni colonne ignorée ni champ laissé à zéro en silence. Deux colonnes de résultat de même nom (`users.id` et `orders.id` dans une jointure) sont aussi une erreur : donne un alias à l'une avec `.As("order_id")`.
- Les champs non exportés sont ignorés ; `db:"-"` ignore un champ exporté ; une struct anonyme embarquée sans tag voit ses champs mis à plat.
- Une colonne calculée sans alias a le nom que PostgreSQL lui donne (`count`, `sum`, `coalesce`, `?column?`) : donnez-lui toujours un alias avec `.As("total")` quand elle va dans une struct.
- Le plan par nom est calculé une fois par (type, liste de colonnes) puis gardé en cache.

Lecture par position, avec une struct à vous :

```go
//qlx:row
type UserSummary struct {
    ID    int64
    Email string
    Posts int64
}

sel := q.Select(Users.ID, Users.Email, q.Count(Posts.ID).As("posts")).
    From(Users).LeftJoin(Posts).On(Posts.AuthorID.EqX(Users.ID)).GroupBy(Users.ID)
rows, err := client.All[UserSummary](ctx, sel)
```

Après `qlx rows`, `UserSummary` a une méthode `ScanTargets` qui suit l'**ordre des champs** : l'ordre du `Select` doit être le même. Deux colonnes de même type permutées ne produisent aucune erreur, seulement des valeurs échangées : l'analyseur le détecte en comparant les noms (V018).

Ce que pgx sait lire dans un champ (vérifié sur PostgreSQL 16 avec `VerifyRow`) :

| Colonne | Champs acceptés | Refusés |
| --- | --- | --- |
| `int2`, `int4`, `int8` | tout entier, `float64`, `string` (rendu en texte) ; `qt.Null[...]` ou pointeur si nullable | `bool` |
| `float4`, `float8` | `float64`, `float32` ; un entier est accepté mais échoue si la valeur n'est pas entière | |
| `numeric` | `qt.Numeric`, `float64`, ou votre type d'override | |
| `text`, `varchar` | `string`, `[]byte` | un nombre |
| `bool` | `bool` | un entier |
| `timestamptz`, `timestamp`, `date` | `time.Time`, les types `qt` correspondants | `string` |
| `bytea` | `[]byte` | |
| `T[]` | `[]T` | un scalaire |
| `uuid` | `uuid.UUID`, `[16]byte`, `string` | |
| `jsonb` | `qt.JSONB[T]`, `[]byte`, `string` | |
| enum | le type Go généré | |

Un plan de lecture qui existe n'exclut pas une erreur de valeur : un `int8` trop grand pour un `int16`, un `float8` non entier dans un `int64`, un `NULL` dans un champ qui ne peut pas le contenir. C'est ce que l'analyseur et `VerifyRow` ne peuvent pas décider.

### 10.11 Vérifier les mappings

Du plus tôt au plus tard :

| Contrôle | Voit | Ne voit pas |
| --- | --- | --- |
| compilateur | colonnes inexistantes, types des opérandes, `T` contre `qt.Null[T]` dans les expressions | le type `R` de `client.One[R]` : il n'est pas lié au `Select` |
| `qlx gen` / `qlx check` | schéma et code généré désynchronisés | |
| analyseur V018 | `R` contre les colonnes d'un `Select` écrit dans le source : nombre, noms, types Go, `NULL` possible (y compris côté optionnel d'une jointure externe), ordre | statements construits dans des fonctions ou des boucles |
| `pgxexec.VerifyRow[R]` dans un test | tout statement, sur un vrai serveur, sans l'exécuter : nombre, noms, plan de lecture pgx de chaque colonne | un `NULL` réel |
| `pgxexec.VerifySchema` au démarrage | le schéma réel contre le code généré | |
| un test avec des lignes réelles, dont une avec `NULL` | ce que rien d'autre ne voit | |

Une règle pratique : pour chaque requête enregistrée, un test qui appelle `VerifyRow` avec le type de résultat de production, plus un jeu de données qui contient au moins une ligne avec des `NULL` dans chaque colonne nullable ou optionnelle.

## 11. Fonctions et opérateurs PostgreSQL

Chaque fonction et opérateur du catalogue est un wrapper typé, généré depuis le catalogue du serveur (`pgcat.json`, PG 16 à 19) :

```go
import "example.com/qlx/pg"                 // façade plate : pg.Lower, pg.Concat, ...
import "example.com/qlx/pgcat/num"           // ou par domaine : text, num, array, datetime, jsonb, fts, geo, network, ranges, binary, xml, sys, misc

q.Select(pg.Lower(Users.Email)).From(Users)
q.Select(num.StddevInt8(Orders.Total).
        Filter(Orders.Status.Eq("paid"))).
    From(Orders) // agrégat typé + FILTER
```

### 11.1 Comment les wrappers se typent

| Cas | Forme Go |
| --- | --- |
| Fonction ordinaire | `Lower(a Operand[string]) Expr[string]` |
| Résultat pouvant être NULL | `Expr[qt.Null[T]]` (entrée NULL pour une fonction non stricte ; `lower(range)`, `->>`, `regexp_match`... pour les cas où le catalogue dit « strict » mais le résultat peut quand même être NULL) |
| Variadique | `Concat(rest ...qlx.Value)` ; `FormatTextAny(fmt, rest ...qlx.Value)` |
| Retour `void` | `Expr[qt.Void]` (verrous advisory, `pg_notify`...) |
| Types polymorphes | génériques : `Operand[E]`, `qt.Range[E]`, `qt.Multirange[E]` |
| Agrégat | `AggExpr[R]` : accepte `Filter`, `Distinct`, `OrderBy`, `Over` ; NULL sur zéro ligne sauf `count`/`regr_count` |
| Fonction set-returning scalaire | `qlx.TableFunc` : `num.GenerateSeriesInt4Int4(a, b).As("s", x)` puis `q.RefNum(s, x)` ; le type de la colonne est celui du `Field` que vous déclarez |
| Fonction à colonnes `OUT` / `TABLE` | `TableFunc` + colonnes typées (toutes nullables ; `catcode` est un `qt.Char`) : `cols := sys.PgGetKeywordsCols` ; `e := sys.PgGetKeywords().As("e", cols.Fields()...)` ; `q.Ref(e, cols.Word)` |
| Fonction ajoutée en PG N | erreur de rendu nommant la version si la cible est plus ancienne |

Fonction dont le record change entre majeurs (`pg_stat_get_wal`, `pg_get_replication_slots`...) : un wrapper par forme, nommé par ses versions (`PgStatGetWalUpTo17`, `PgStatGetWalV18`, `PgStatGetWalFrom19`) ; le nom sans suffixe n'existe plus, utilisez le nom versionné.

Collisions de noms entre types (`Lower` texte contre `Lower` d'intervalle) : le nom reste simple dans le domaine principal ; les autres reçoivent un suffixe de type (`BitAndInt4`, `StddevFloat8`). Les variantes à arguments nullables finissent par `N` (`LowerN`).

Exemples de wrappers de différentes formes :

```go
text.Concat(Users.Email, q.Val("-x"))                              // variadique : Expr[qt.Null[string]]
sys.PgAdvisoryLockInt8(q.Val(int64(42)))                            // void : Expr[qt.Void]
fts.SetweightTsvectorChar(vec, q.Val(qt.Char('A')))                // type "char"
jsonb.JsonbPathExists(doc, q.Val(qt.JSONPath("$.a")), vars, q.Val(true))
```

Écrits à la main dans le paquet principal, parce qu'ils ont une forme propre : `Count`/`CountAll`, `Sum`, `Avg`, `Min`, `Max`, `StringAgg`, `ArrayAgg`, agrégats ordered-set (`PercentileCont`, `PercentileDisc`, `Mode`), les 15 fonctions de fenêtre, `Coalesce`, `Case`, `Cast`, constructeurs SQL/JSON, XML (`XMLElement`, `XMLTable`...), `CurrentDate/Time/Timestamp`, `LocalTime`, `Unnest`, `GenerateSeries`.

Pas générés : fonctions de type `internal`/`cstring`/`trigger` (réservées au serveur), fonctions d'entrée/sortie de types, implémentations d'opérateurs (utilisez l'opérateur), types statistiques rares (`pg_ddl_command`, résumés BRIN). Une fonction absente se signale ; elle ne se contourne pas par du SQL brut (§15).

Extensions : `pgcat/ext/vector` (pgvector 0.8.7), `pgcat/ext/hstore`, `ltree`, `citext`, `pgtrgm` et `postgis` (PostGIS 3.7.0) — tous les ledgers livrés sont fusionnés 16–19 (activez-les dans `extensions:` pour avoir aussi les types de colonnes). Un littéral doit être casté vers le type de l'extension avant d'atteindre une fonction surchargée : `q.Cast(q.Val(qt.Vector{1, 2}), q.NewPgType[qt.Vector]("public", "vector"))`. PostGIS enveloppe 624 fonctions et 52 opérateurs (les fonctions de fenêtre, comme `ST_ClusterDBSCAN`, se terminent par `Over`) ; les types `geometry` et `geography` sont mappés, les valeurs circulent en hexadécimal WKB étendu.

### 11.2 Opérateurs

Les opérateurs sont des wrappers comme les fonctions (`text.` pour `||`, `jsonb.` pour `->`, `array.` pour `@>`, `network.` pour `<<`...). La [référence](pgcat/) liste chaque forme avec sa plage de versions et sa volatilité.

### 11.3 Versions PostgreSQL

Une construction plus récente que votre plus ancienne cible est une erreur de rendu qui nomme la version (`IGNORE NULLS` en PG 19, `RETURNING OLD/NEW` en PG 18, `JSON_SERIALIZE` en PG 17...). L'erreur enveloppe `qlx.ErrUnsupportedByServer`. Avec `targets: [18, 19]`, ce qui est 19-seulement est refusé au build par l'analyseur (V009) et au rendu sur un serveur 18.

## 12. Vérifications et tests

### 12.1 Qui attrape quoi

| Niveau | Attrape |
| --- | --- |
| Compilateur | types, nullabilité, mélange d'IDs de tables, colonnes inexistantes, constructeurs d'insertion incomplets |
| Rendu | portée des colonnes, `GROUP BY`, colonnes requises, `UPDATE`/`DELETE` sans condition, version PG |
| Analyseur | voir ci-dessous |
| `PREPARE` réel | tout ce que seul le serveur sait : `qtest.Dump` puis `qlx prepare -queries queries.json` |

L'analyseur est le seul contrôleur statique : `go install github.com/noobmaisfier/qlx/analyzer/cmd/qlxvet@latest`, puis `go vet -vettool=$(which qlxvet) ./...` (il tourne aussi dans gopls et golangci-lint). `qlx vet` n'existe plus. Règle : une erreur *présente* dans le code (colonne assignée deux fois) est toujours signalée ; une partie *absente* (pas de `Set`) l'est seulement quand la chaîne est transmise telle quelle (argument, littéral composite, ou `return` dont le résultat est `qlx.Statement`) ; une chaîne gardée dans une variable ou renvoyée comme builder (`SelectQuery`, `TableFunc`...) peut être complétée plus loin. Un argument que l'analyseur ne sait pas résoudre (`args...`, fonction d'aide) le rend silencieux, jamais approximatif :

| Code | Signale |
| --- | --- |
| V001 | résultat d'un builder jeté (les builders sont immuables) |
| V002 | `Update`/`Delete` transmis sans `Where` ni `All` |
| V003 | nom de `Register` non constant ou en double |
| V004 | résultat ou erreur de `SQL`/`Render` ignoré |
| V005 | `Register` dans un corps de fonction |
| V006 | colonne d'une table absente de `FROM`/`JOIN`/`USING` |
| V007 | agrégat mélangé à des colonnes nues sans `GroupBy` |
| V008 | `INSERT` qui ne renseigne pas toutes les colonnes obligatoires |
| V009 | fonction, méthode ou option `EXPLAIN` dont la plage de versions ne couvre pas `-targets` |
| V010 | `//qlx:ignore` sans raison |
| V012 | partie obligatoire absente : `UPDATE` sans `Set`, `INSERT` sans ligne, `MERGE` sans `Using`/`On`/`When`, `DoUpdate` sans assignation, `CASE` sans `When`, `Truncate()` vide... |
| V013 | parties contradictoires ou dupliquées : colonne assignée deux fois, `Limit` avec `FetchFirst`, `WithTies` sans `FetchFirst`/`OrderBy`, lignes de colonnes différentes, `INSERT ... SELECT` ou opérandes d'une union de largeurs différentes |
| V014 | colonne sélectionnée à côté d'un `GroupBy` qui ne mentionne pas sa table |
| V015 | option `EXPLAIN` qui exige `Analyze` (`Wal`, `IO`, `SerializeText`...) ou l'exclut (`GenericPlan`) |
| V016 | `ForUpdate().Of(t)` avec une table absente de `FROM`/`JOIN` |
| V017 | `SearchDepthFirst`/`SearchBreadthFirst`/`Cycle` sur une CTE non récursive |
| V018 | type de résultat qui ne correspond pas au `Select` : nombre de colonnes, noms de champs, types Go, `NULL` dans un champ non nullable, ordre des champs, deux colonnes de même nom lues par nom, une colonne entière ou id lue dans un `string`, un id d'une autre table |
| V019 | fonction de fenêtre dans `Where`, `Having`, `On` ou `GroupBy` (PostgreSQL l'interdit : filtrer dans une sous-requête ou une CTE) |
| V020 | fenêtre nommée utilisée par `Over(w.Spec())` / `w.Extend()` mais absente de `Windows(...)` de la requête |
| V021 | `Func` sans `As`, `JSONTable`/`XMLTable` sans colonne ou avec un alias vide |
| V022 | variable `$x` d'un chemin JSON non passée par `Passing(Pass("x", ...))`, ou `KeepQuotes`/`OmitQuotes` avec un `WITH WRAPPER` |
| V023 | `Grant`/`Revoke` : privilège, `OnTables`, rôles manquants ; `To`/`From` inversés ; `WithGrantOption` sur REVOKE, `Cascade` sur GRANT |
| V024 | `Refresh...Concurrently()` avec `WithNoData()` ; `SetConstraints` sans nom |
| V025 | `SearchOrder()` / `CycleMark()` sur une CTE construite sans `SearchDepthFirst`/`SearchBreadthFirst` / `Cycle` |
| V026 | colonne de conflit ou affectation (`Set`, `Row`, `DoUpdate`) qui désigne une colonne d'une autre table que celle écrite |
| V027 | `ToOrDefault` dans une liste `SET` (`Set`, `DoUpdate`, `ThenUpdate`) : un champ absent remettrait la colonne à son défaut, `ToIf` la laisse intacte |
| V028 | verrou de lignes (`ForUpdate`, `ForNoKeyUpdate`, `ForShare`, `ForKeyShare`) sur une requête avec `Distinct`, `GroupBy`, `Having`, un agrégat ou une fonction de fenêtre : PostgreSQL le refuse |
| V029 | `Distinct` avec un `OrderBy` sur une colonne non sélectionnée ; `DistinctOn` dont les expressions ne commencent pas le `OrderBy` |
| V030 | `ToNull()` sur une colonne dont le type Go ne peut pas contenir `NULL` (le serveur répond 23502) |

Un constat accepté se supprime avec un commentaire sur la même ligne ou la précédente : `//qlx:ignore <raison>`. Avec `-audit`, chaque suppression est elle-même listée (V011).

### 12.2 Tester vos requêtes

Sans base, rendez et comparez à un fichier de référence (« golden ») :

```go
func TestUsersByTier(t *testing.T) {
    sql, args, err := q.SQL(q.Dialect{Version: q.PG18}, usersByTier("pro"))
    if err != nil { t.Fatal(err) }

```

## 13. Recettes

### 13.1 Pagination par curseur (keyset)

```go
func nextPage(afterID int64, size int64) q.Statement {
    return q.Select(Orders.ID, Orders.Total).From(Orders).
        Where(Orders.ID.Gt(afterID)).
        OrderBy(Orders.ID.Asc()).
        Limit(size)
}
```

Contrairement à `Offset`, le coût ne grandit pas avec la profondeur, et la forme est la même pour toutes les pages.

Avec une clé composée (ici le plus récent d'abord, l'identifiant départageant), `KeyAsc` / `KeyDesc` déclarent la clé sans valeur, `KeyOrder` en tire l'`ORDER BY`, et `.After(v)` lui ajoute, typée comme la colonne, la valeur de la dernière ligne vue ; `q.After` produit le prédicat :

```go
func page(last *Cursor, size int64) q.Statement {
    byDate, byID := q.KeyDesc(Orders.CreatedAt), q.KeyAsc(Orders.ID) // declared without a value
    var after q.Pred                                                  // absent on the first page
    if last != nil {
        after = q.After(byDate.After(last.CreatedAt), byID.After(last.ID))
    }
    return q.Select(Orders.ID, Orders.Total).From(Orders).
        Where(after).
        OrderBy(q.KeyOrder(byDate, byID)...).
        Limit(size)
}
```

Sans clé (première page), `q.After()` est un prédicat absent. Quand toutes les clés vont dans le même sens, `After` rend une comparaison de lignes `(a, b) > ($1, $2)` que PostgreSQL résout par un seul parcours d'index ; en sens mixtes il rend l'expansion équivalente `a < $1 OR (a = $2 AND b > $3)`. Les colonnes de clé doivent être `NOT NULL` et, ensemble, uniques (terminez par la clé primaire) : un `NULL` ne se compare jamais, et deux lignes de même clé seraient sautées ou répétées à la frontière d'une page.

### 13.1b Tri choisi par le client

Une chaîne de tri venue d'une URL ne doit jamais atteindre le SQL. `NewSorts` déclare la liste blanche ; un nom inconnu, un doublon ou trop de clés donne une erreur `ErrSort` (à renvoyer en 400) :

```go
var orderSorts = q.NewSorts(map[string]q.Orderable{
    "total":   Orders.Total,
    "created": Orders.CreatedAt,
}).Default(Orders.CreatedAt.Desc()).Tiebreak(Orders.ID.Asc())

order, err := orderSorts.Parse(r.URL.Query().Get("sort")) // "-total,created"
if err != nil { /* 400 */ }
sel = sel.OrderBy(order...)
```

`-` devant un nom trie en décroissant. Le départage est toujours ajouté en dernier, ce qui rend l'ordre total. Le nombre de formes de requête reste borné par la liste blanche.

### 13.2 Compteur atomique

{{ex:upsert}}

L'upsert avec `Excluded()` ou une expression sur la colonne existante évite le « lire puis écrire » et ses conflits.

### 13.3 File de travail

Voir le verrouillage `FOR UPDATE SKIP LOCKED` (§4.12), dans une transaction : sélectionner le lot, le traiter, le marquer terminé, valider.

### 13.4 Charger beaucoup de lignes

Moins de 1 000 lignes : un `INSERT` multi-lignes (§5.1). Au-delà : `pgxexec.CopyIn` (§9.3).

### 13.5 Recherche avec filtres facultatifs

```go
func search(email string, tier qt.Opt[string], minBalance qt.Opt[int64]) q.Statement {
    sel := q.Select(Users.ID, Users.Email).From(Users)
    if email != "" {
        sel = sel.Where(Users.Email.ILike("%" + email + "%"))
    }
    return sel.Where(Users.Tier.EqIf(tier), Users.Balance.EqIf(minBalance)).OrderBy(Users.ID.Asc()).Limit(50)
}
```

Chaque combinaison de filtres présents est une forme, rendue une seule fois.

### 13.6 Soft delete

Un champ `deleted_at timestamptz` : `Update(...).Set(T.DeletedAt.ToX(q.Now()))` à la place de `Delete`, et `Where(T.DeletedAt.IsNull())` dans vos requêtes de lecture (placez-le dans une fonction `alive()` partagée).

## 15. Ce qui n'existe pas (volontairement)

- Pas de SQL brut : `Raw(...)` n'existe pas. Une forme non modélisée se signale (ledger de grammaire) et s'ajoute au lieu de se contourner.
- Pas de DDL : le schéma vit dans vos migrations SQL.
- Pas de pointeurs pour NULL : `qt.Null[T]`.
- Pas de constructions que le serveur refuse : `XMLTABLE` avec `DEFAULT` d'espace de noms, `XMLSERIALIZE ... bytea`, etc. n'ont pas de builder.

## 16. Dépannage

| Message | Cause | Remède |
| --- | --- | --- |
| `qlx check` échoue | code généré ou `schema.lock` modifié/périmé | `qlx gen` |
| `ErrUnsupportedByServer` | construction plus récente que la cible ou le serveur | éviter l'usage, ou monter `targets` |
| `ErrShape` « UPDATE has no WHERE » | `Update`/`Delete` sans condition | `Where(...)` ou `All()` |
| `ErrShape` colonne obligatoire | `INSERT` sans une colonne `NOT NULL` sans défaut | la renseigner ; utiliser `NewXInsert` |
| `ErrSort` | nom absent de la liste blanche, élément vide, doublon ou trop de clés | renvoyer 400 ; corriger la map `NewSorts` ou la chaîne de tri |
| `qt.ErrIDKey` | `SetIDKey` non appelé | `qt.MustSetIDKey` au démarrage |
| `qt.ErrBadID` | texte d'ID faux ou d'une autre table | rejeter la requête (400) |
| `qt.ErrIDRange` | entier hors de 0..2^48−1 | n'arrive pas avec une identité normale |
| `pgx.ErrTooManyRows` / `ErrNoRows` | `One` sur plusieurs lignes ou zéro | `Maybe` ou `All` |
| `Evictions` du cache de formes qui monte | formes non bornées | `col.Any(slice)`, pas de colonnes dynamiques |
| « cannot scan ... into *qt.X » | type texte sans `Scan` | utiliser le type `qt` prévu (tous les types de §10 en ont un) |
| `go.sum` manquant | dépendances non résolues | `go mod tidy` |
| V006 / V007 / V008 | colonne hors portée, agrégat sans `GroupBy`, `INSERT` incomplet | corriger la requête |
